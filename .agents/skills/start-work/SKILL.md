# Start work

Read AGENTS.md, docs/project.md, docs/work-management.md and docs/workflow.md from the repository root. Reuse unchanged context. For changes covered by docs/android-studio.md, inspect the relevant current Cursor implementation/tests and linked Issue/PR evidence before design; record a fixed source revision and applicability in this Issue. Unrelated CLI-only or wording work does not require a full upstream survey. For instructions/Skills also read docs/context.md.

Inspect the Issue/comments, related PRs, ownership, dependencies, branch, worktrees and dirty state. Search before creating an Issue. Claim scope, owner, base, target, reviewer, GUI need and next action, then read back. Inspect native Development links separately from body references under docs/work-management.md; record missing links and the default-branch closure boundary. Unreleased claims do not expire. Resume in your existing worktree; take over only after reassignment and old-writer stop, in a separate worktree.

Fetch without disturbing edits. Branch from the configured integration branch into `agent|codex|claude|cursor/<issue>-<slug>` in a dedicated worktree. Remove an inherited upstream to the integration branch. Install hooks with `python3 scripts/bootstrap.py` after inspecting them; preserve custom hooks on conflict.

For develop bug Issues, classify Acceptance repair as none or the preserved original-NG Issue comment ID; follow docs/verification/README.md for corrective scope, fixed failure provenance and all failed guarantees. Do not use a label or omitted declaration to hide acceptance NG.

Record observable acceptance, real project checks and remaining GUI/release conditions in the Issue. Create a Draft PR on the first meaningful push. Apply the canonical PR title rule in docs/work-management.md: `type: 日本語の要約 (#N)`, lower-case type chosen from the actual change, no scope, one owning Issue suffix matching branch/body. Preserve actual breaking-change `!` with rationale; do not rewrite Issue titles or commit/closed-PR history. Read the live title back at creation, ready and correction restart; keep related Issues and closure instructions in their existing body/native workflow. Populate and read back its native assignee, type/priority/current PR-status labels, actual Project/Milestone and review/request state under docs/work-management.md. GitHub accounts differ from internal writer/reviewer sessions; never invent identities or copy Issue status blindly. Recheck at ready or correction restart. Apply docs/work-management.md's Development timing: manually link develop PRs and read both ends/Issue state; defer closing references for unfinished default-main Issues until post-merge completion and manual closure. Record the reason, owner and next safe action. Optional branch links must reuse the dedicated branch and be rechecked after PR creation; never assume an automatic link or create an extra branch just for display. Continue through finish-work; setup or a Draft PR alone is not completion. Referencing agents, server settings or GUI capabilities does not authorize their use.

For team work, use docs/team-communication.md and the supplied PM/liaison routes. Keep technical results in concise agent packets; route genuine human decisions through PM to the liaison using native choice cards. Do not turn routine work or handoffs into new human approval gates. Preserve higher-priority output and actual tool permission requirements.

Apply docs/verification/responsibility.md to existing and future tests. Identify our owned guarantee and observable defect before choosing the minimum faithful method; use trusted effective contracts, preserve immutable originals/failures and distinguish full-file proof from representative native integration. Do not create new approval gates or rebuild/retest unchanged artifacts merely for an explicitly reviewed method revision. Reassessment needs exact provenance, conditions and complete effective coverage, not relabeled old PASS.

Use guarantee → required evidence/precision → minimum feasible method for all test families. Read the trusted effective method revision; do not reinstate historical counts/deadlines/same-run/instant-cleanup recipes. Keep owned data/timing/content, failure/atomicity/pin, ownership and actual integration. Reuse unchanged artifact-bound facts and test only missing purposes; method revision is not execution. Review necessity and coverage, including separate native/regression/FILE facts, rather than conformity to an obsolete recipe.

For product repairs, apply the guarantee-level impact certificate in docs/verification/README.md when reusing unaffected successful facts across changed ZIPs. Keep immutable originals and both identities, current load/integration facts, all effective contracts/deferrals and original-NG repair gates. Require substantive independent provenance/impact/coverage review and a trusted-main Issue certificate; unknown impact or affected guarantees need fresh facts. A policy-only update does not require rebuilding the product. Do not restore strict whole-artifact or prior-promotion requirements from the older reuse path to this separate assessed-fact path.
