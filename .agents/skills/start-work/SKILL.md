# Start work

Read AGENTS.md, docs/project.md, docs/work-management.md and docs/workflow.md from the repository root. Reuse unchanged context. Start from this repository’s requirements, effective contracts, implementation/callers and tests. External knowledge reuse under docs/android-studio.md is optional; consult a source only for a concrete task need and record fixed evidence/applicability when adopting it. No Cursor survey or non-consultation declaration is required. For instructions/Skills also read docs/context.md.

Inspect the Issue/comments, related PRs, ownership, dependencies, branch, worktrees and dirty state. New Issue titles follow docs/work-management.md’s existing six-label mapping to `type: 日本語の要約` (QA: `test: #origin 要約`); preserve legacy read compatibility. Do not rename repository Issues until adopted policy and PM’s fixed OPEN-only list/sole metadata assignment; preserve all non-prefix content and native metadata. Search before creating an Issue. Claim scope, owner, base, target, reviewer, GUI need and next action, then read back. Inspect native Development links separately from body references under docs/work-management.md; record missing links and the default-branch closure boundary. Unreleased claims do not expire. Resume in your existing worktree; take over only after reassignment and old-writer stop, in a separate worktree.

Use `scripts/workflow/project_item.py` for Project #5 item additions and field changes, with the freshly confirmed own-repository Issue/PR URL. Follow docs/work-management.md's Project mutation boundary; do not submit copied opaque IDs through another route.

Fetch without disturbing edits or pruning unpreserved tracking-only work; use `git fetch --no-prune origin` until the workflow branch-lifecycle preservation check is complete. For newly created branches after this policy is adopted, branch from the configured integration branch into `codex/<issue>-<type>-<short-english-kebab-purpose>` by default in a dedicated worktree, following docs/work-management.md. Use the actual PR type, one owning Issue and lower-case ASCII words separated by single hyphens. Other authorized agent prefixes follow the same suffix. Validate with native `git check-ref-format --branch`; do not rename existing/open/historical refs. Existing parsers retain their old readable forms, and type/purpose/Issue consistency needs start and fixed-review readback. Name newly created work commits after adoption `type: 日本語の要約 (#N)` under the same work-management rule, optional body after a blank line. Use the actual per-commit type and owning Issue; preserve existing history and the documented generated integration/base-merge exceptions. Remove an inherited upstream to the integration branch. Install hooks with `python3 scripts/bootstrap.py` after inspecting them; preserve custom hooks on conflict.

For develop bug Issues, classify Acceptance repair as none or the preserved original-NG Issue comment ID; follow docs/verification/README.md for corrective scope, fixed failure provenance and all failed guarantees. Do not use a label or omitted declaration to hide acceptance NG.

Preserve actual breaking-change `!` with rationale; do not rewrite Issue titles or commit/closed-PR history. Populate and read back its native assignee, type/priority/current PR-status labels, actual Project/Milestone and review/request state under docs/work-management.md. GitHub accounts differ from internal writer/reviewer sessions; never invent identities or copy Issue status blindly. Recheck at ready or correction restart. Apply docs/work-management.md's Development timing: manually link develop PRs and read both ends/Issue state; defer closing references for unfinished default-main Issues until post-merge completion and manual closure. Record the reason, owner and next safe action. Optional branch links must reuse the dedicated branch and be rechecked after PR creation; never assume an automatic link or create an extra branch just for display. Continue through finish-work; setup or a Draft PR alone is not completion. Referencing agents, server settings or GUI capabilities does not authorize their use.
