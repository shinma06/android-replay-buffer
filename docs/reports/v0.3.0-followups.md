## 2. 音声比較：`a6d8c0f` → `594a0dd` → `5af6ac2`

3 コミットは連続した `develop` マージコミット: `a6d8c0f` (PR #473 tap-display) → `594a0dd` (PR #476 clock-t3-boottime-axis) → `5af6ac2` (PR #478 clock-t5-cleanup)。**音声専用ファイル（scrcpy audio patch、`AudioRecordReader`、音声 capture worker、`record_audio` 設定、音声 wire protocol）の差分は全期間でゼロ。** 変更は全て時計リファクタに伴うマッピング経路のもの。

### 変わらなかったもの（3 コミット同一）

- `record_audio` 設定・`ReplaySettingsJson`・CLI/MCP・設定 UI（差分ファイル一覧に非該当）
- `plugin/src/scrcpy/` 配下（音声 patch・`AudioRecordReader`）: `git log a6d8c0f..5af6ac2` で変更なし
- `audioCoverage()`（`SaveWriter.kt:1062`）: 両端でバイト一致。`coverage.audio` の `state / requested / availableSeconds / reason / note` 出力は同一
- `audio_track`（replay.json）: `codec=AAC-LC / sample_rate / channels / source / time_source / segments` 出力は同一
- `AudioCaptureTest`・`DeviceCaptureAudioStateTest`: テスト自体に差分なし
- 録音 fixture（mp4/aac 等）: リポジトリ内に存在せず、実測比較は不可能（fixture 不存在を確認済み）

### 実質的な差分（全て `594a0dd` = PR #476 由来）

`5af6ac2` (PR #478) 側の音声関連差分は `time.epoch` → `time.region`・`anchorsByEpoch` → `anchorsByRegion`・`MovieAnchor.epoch` → `.region` の**リネームのみ**で、意味的変更なし。実質変更は以下の 2 点。

1. **`planAudio` の行受理条件から「clock gap との交差による除外」が削除**（`SaveWriter.kt`）
   - `a6d8c0f`: `sequence != null && windowKnown && uncertainty != MAX && videoScopes.none { clock gap と交差 }`
   - `594a0dd`〜: `row.time.sequence != null && windowKnown && uncertainty != MAX`
   - 意味: 「解消済みの時計不足区間（同じ時計区間で回復が証明された測定不達）」内の音声行は、以前は AAC track から**除外**されていたが、現在は前後の測定値から換算されて**含まれる**。`docs/design/timeline.md` の設計意図（「区間内の frame・ログ・タップ・音声は前後の sample で変換し、保存の不足の種類にも数えない」）と一致する仕様改善であり、受入上のリスクは低い

2. **音声行の換算ヒントが epoch → region + `reference` segment に変更**（`CaptureStore.kt:485` 付近）
   - `audio.map { it.mapped(clock.video(it.pts, it.host, it.time.region, reference)) }`（`reference` = 保存窓の boot segment）
   - `planAudio` では `anchors[row.time.region]?.movieTime(point)` で movie timeline へ配置（本体は epoch→region リネームのみでロジック同一）
   - 意味: 別 boot の音声行は `sequence == null` となり AAC から除外される。旧 model では boot 跨ぎは host 時計で sequence を橋渡しできたが不確実な換算だったため、**厳密化**（除外方向の変更）であり受入観点では問題なし
   - 加えて、音声 gap を閉じる際に `acrossBoot()` で boot 跨ぎなら `boundaryUncertaintyNs=MAX` を付与（`CaptureStore.kt:390,895`）

### 結論（音声）

- `端末の再生音` 受入行が検証する挙動（AAC track の有無、`coverage.audio.state=CAPTURING` / `requested`、`record_audio=false` で track 無し + `requested=false`、beep 同期 ~0.1 秒）に影響する差分は**なし**
- 単体テスト `AudioCaptureTest.savedMp4HasAnAacTrackAlignedWithTheVideoAndCoverage` が unit レベルで AAC track・coverage・movie 先頭同期を検証済みで PASS
- **エミュレータで残る確認**: 実機相当の `AudioRecord` timestamp→AAC encoder 遅延（白表示→beep 中央値 ~0.1 秒）と `ffprobe` での実 AAC track 確認、`record_audio=false` の end-to-end。API 28 は playback capture 非対応（<13）で `coverage.audio.state=UNAVAILABLE` となる想定（受入表でも音声は API 28 の確認対象外）

## 3. 時計注入/回復（>5 秒の clock/epoch 途切れを含む）

### 実装の追跡結果（`5af6ac2`）

測定経路: `DeviceCapture.kt` が 1 秒周期で端末 DEX helper へ nonce 付き測定を送り、`store.clockStatus(store.clock.add(...))`（`DeviceCapture.kt:352`）へ渡す。worker 失敗（process 停止・3 秒 expiry・応答異常）は `clockStatus(false)`（`DeviceCapture.kt:131`）→ `CaptureStore.clockStatus` が「clock」gap を**最後の正常測定の時計区間**で開く（`CaptureStore.kt:336-353`）。

モデル変更（`a6d8c0f` → `5af6ac2`）:
- 旧: 5 秒超の測定不達（`missingAnchor`）や clock worker 再起動（`clock.boundary()` 呼出）はそれ自体が境界 = 新 epoch。**現行では削除済み**（`CaptureClock.kt:54` コメント「A measurement outage alone is no boundary」、`DeviceCapture.kt` の boundary 呼出削除）
- 現行: 不達は境界にしない。次の正常測定が同じ boot かつ mono/Epoch offset が読取誤差内で連続なら**同じ時計区間**のまま途切れ間の記録も換算可（`resolvedClock`、loss ではない）。offset 不連続・boot 変化・PTS 逆行のみが `startRegion()` を開く
- RTT >40ms の測定は `valid` だが `hostAnchored` でない（`ClockSample.kt`）: 映像/ログ変換には使えるが、受付時刻等の host→端末推定 anchor には使わない（`docs/design/timeline.md` で明文化）

クラッシュ自動保存の時計ゲート（`CrashAutosave.kt` + `CaptureStore.refreshAuto`）:
- 1 秒周期の control poll（`ReplayCore.kt:72-74`）が `configureAuto` → `refreshAuto` を回し、context 成立 + `clock.certain()`（最新 sample が valid・同時計区間・受信 5 秒以内）なら `CrashBarrier` を立てる
- certain でない間は `autosave.refresh(null, host, clockRegion=現在区間)` が**同じ時計区間のまま最大 5 秒（`CRASH_RECEIPT_NS`）の保持**を開始。保持中の Java 報告は `deferred` として保留し、回復後の換算で再判定（`resolveHeld`）
- 保持が 5 秒を超える、または時計区間/boot/generation/device が変わる → `NOT_SAVED_CLOCK_UNKNOWN`（「報告の時計対応を確認できません」、`ReplayModels.kt:131`）で破棄・保存しない

### テストで証明されること vs エミュレータが要ること

証明済み（単体レベル、注入は `store.clock.add` の不正測定・時間経過・boot 変更で再現）:
- 保持 ≤5 秒の同区間回復 → 保存（不足区間は解消済みとして loss に数えない）
- 保持 >5 秒・区間/boot 境界跨ぎ → `NOT_SAVED_CLOCK_UNKNOWN` で保存しない
- 途切れ中に受信した Java 報告の遅延判定と回復後の再換算

エミュレータ/実機が要るもの（**未確認**）:
- 実際の注入経路: clock 測定 DEX process の kill/再起動、`adb shell date`/reboot による wall/boot 変化、`am crash` との実時間インタープレイ（`am_crash` 検出・ps poll・受信順序）
- 受入表の「5 秒以内の時計の不足区間…回復後に保存 / 5 秒を超える途切れ…保存しない」は**「観測された保持 ≦5 秒」が実際のゲート**。poll が 1 秒周期なので、壁時計の測定不達が約 10 秒を超えれば決定的に拒否、5〜10 秒は注入と poll の位相で保存になり得る（上記追加テストが証明）。エミュレータ検証では「途切れ >5 秒」だけを注入しても結果は不定になり得るため、**明確に拒否を見るには 10 秒を大きく超える途切れ**が必要
- 観察: schema 4 では解消済みの時計途切れは `gaps` にも `timebase.clock_steps` にも専用エントリを持たない（`timebase.samples` の読取履歴でのみ痕跡が残る。`SaveWriter.kt:207-216,887-896`）。受入表の「`replay.json` に時計の不足区間が残る」という記述は schema 4 前の文言で、解消済み途切れに対しては `samples`/`boot_segments` の確認に読み替える必要がある可能性。**未解消の途切れだけが `clock_steps` の `unmeasured` として残る**（`docs/crash-autosave.md` の記述とも要整合の確認余地）
