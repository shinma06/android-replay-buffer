# リリースの規則

`main` は安定版、`develop` は最新版です。完成したTrailは `develop` へどんどんマージし、`develop` の最新は `early` プレリリースで使えます。`main` へは、受入を通った `develop` だけを入れます。

## 版番号

[Semantic Versioning](https://semver.org/lang/ja/) に従います。1.0.0になるまでは、互換の壊れる変更もマイナー版で出します。

| 上げる桁 | 条件 |
|---|---|
| パッチ（0.2.**1**） | 不具合の修正だけ |
| マイナー（0.**3**.0） | 機能の追加、またはCLI・MCP・設定・保存形式の互換を壊す変更を1つでも含む |
| メジャー（**1**.0.0） | 安定版として互換を約束するとき。利用者の判断で決める |

- 開発版（CIのZIP・`early`）は `<次の版>-dev.<commit>` です。次の版は `plugin/gradle.properties` の `devBaseVersion` に書きます
- 正式版は、`main` 上のタグ `vX.Y.Z` からだけ作ります（`release.yml` がタグが `main` 上にあることを確かめます）

## いつ出すか

エージェントが判断し、人の承認は要りません。次のすべてを満たしたら出します。

- `main` にない利用者向けの変更が `develop` にある
- `develop` の先頭で、CIの `test`・`os-parity`（macOS・Windows）が通っている
- その先頭を壊すと分かっている不具合のTrailが開いていない

不具合を急いで直すときも、修正は `develop` に入れてからパッチ版で出します。`main` へ直接の修正は入れません。

## 手順

1. 版番号を上の規則で決める
2. `develop` 先頭のCIが作ったZIPで、[VMでの受入](verification/vm-acceptance.md)を行う。パッチ版は基本の項目と修正した機能、マイナー版以上は全項目
3. `develop` → `main` のPRを作り、受入の結果（確かめたこと・確かめていないこと）を本文に書いてマージする
4. `main` のマージコミットに `vX.Y.Z` のタグを付けて送る。`release.yml` が正式版のZIPを公開し、Latestになる
5. `develop` の `devBaseVersion` を次のマイナー版（例: 0.3.0を出したら0.4.0）に上げる。パッチ版を出した場合は上げない

受入で問題が出たら、リリースを止めて修正のTrailを作ります。直して `develop` に入れてから、手順1からやり直します。
