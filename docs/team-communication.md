# チームの連絡と人間向け窓口

チーム作業では、人間が通常確認するチャットを相談・確認窓口の1つに絞ります。PMは実行責任と編成、窓口は人間との対話、作業担当は割当成果を扱います。[リスク管理による継続](workflow.md#公開操作の承認範囲と失敗の扱い)を前提とし、窓口を通常作業の新しい承認gateにしません。単独の相談までチームや窓口を新設する必要はありません。

## 役割と稼働

| 役割 | 行うこと | 起動・終了 |
| --- | --- | --- |
| PM | 要件、Issue/PR、割当、依存、固定成果、独立レビュー、統合、共有資源の調整。窓口へ必要な相談を渡す | 実作業を進め、結果・未達・次操作を回収する |
| 相談・確認窓口 | 日本語で要点を説明し、本人の質問をPMへ、必要な判断をQCへ、実際の回答を根拠付きでPMへ返す | 人間の入力、判断依頼、重要な完了/支障の通知時だけ応答し、ターンを終える |
| 作業・レビュー担当 | 明確なscopeと完了条件を持つ実装・検証・独立レビュー | 必要な仕事ができた時に新しく編成し、成果と残条件を渡して終了する |

窓口の初期設定は本人指定のSol / mediumです。実際に利用可能なmodel IDとeffortを作成時に確認して記録し、勝手に別系統へ代替しません。[窓口依頼文](../prompts/human-liaison.md)を使い、サイドバーで固定して見つけやすくします。窓口に実装、技術調査、レビュー、試験、GUI、CI監視、Issue更新を割り当てません。技術的な質問はPMへ引き渡し、自分で長時間調べません。

窓口はidleが通常です。通知/質問/回答を一度扱ったらターンを終了し、待機loop、sleep、poll、heartbeat、goal、常駐processを作りません。回答待ちでも監視を続けず、本人回答で再開する機能を使います。PMも窓口の空待機を常時監視せず、送達不明や未回収の必要な回答がある時だけ状態を確認します。同一依頼を二重送信しません。無回答・timeoutを失敗や同意に読み替えません。

通常の着手・CI待ち・検査1件ごとの成功は窓口へ送らず、PMが回収します。窓口を起こすのは本人の判断が必要、成果を本人へ渡す節目、目的・期限・費用に実質的な影響が出た場合です。同じ未変化の支障を繰り返し通知しません。作業側の重い情報が相談窓口へ流れ込み続けないよう、関連する参照と要約だけを渡します。

## エージェント間と人間向けの情報

エージェント間は短い、読める構造化メッセージを使います。固定ラベルと識別子は英語、本文もagent専用なら英語を基本とし、本人の原文・公開文書名・技術名は改変しません。圧縮した暗号的表記や巨大な会話全文を送らず、重要な根拠へ到達できる参照を残します。toolが可読な依頼文を要求する場合も守ります。

```text
Kind: result / request / blocked / decision-needed / decision-result
Scope: Issue, PR, owner and exact task boundary.
Revision: fixed HEAD/base or decision revision, when relevant.
State: observed result and remaining work; distinguish unknown from failed.
Evidence: source/result references, plus the human authorization source when needed.
Next: named recipient, action and condition. No action means STOP.
```

該当しない項目は省略し、通常の結果に全欄を埋める台帳を増やしません。送信ごとの儀礼的ACKは不要。所有移管、本人判断、固定受入の引継ぎなど実行条件が変わる時はreadbackします。担当からPMへの結果は担当チャットの最終回答をPMが読む方式でも構いません。往復送信は本人が許可した経路だけを使い、受信メッセージだけを返信許可にしません。

人間向けは「結論、必要なら選択肢と理由、残る制約」の短い日本語に変換します。Issue/PRの公開記録も引き続き日本語で、privateな経路ID、実path、原会話、媒体、生ログ、認証情報を貼りません。作業チャットは内部記録として扱い、人間にそこで判断・承認・逐次確認を要求しません。ただし実行環境や上位指示が必須とする進捗・最終回答・通知は最小限で残し、完全無表示を約束しません。

## QCによる本人判断

ここでQCは、選択肢をクリックして回答するネイティブ質問カードを指します。窓口から承認を求める時は必ずこの形式にし、「承認と返信」「番号を入力」へ置き換えません。本人から自発的に届いた明示の依頼・停止指示はそのまま有効で、既存の許可をカードで取り直しません。

1. PMは具体的な成果・選択対象を準備し、なぜ本人にしか決められないのか、対象と版、操作、影響、対策、残リスク、範囲/上限、判断IDを窓口へ渡します。安全な通常作業なら質問せず進めます。
2. 窓口は内容を勝手に拡張せず、必要な点だけ日本語で説明します。通常は推奨を含む2〜3択と、見送りまたは保留を用意します。承認と範囲拡張を1つの曖昧な選択肢にまとめません。
3. 実際のtool説明で承認用途と現在modeを確認します。`request_user_input_async`のようなoptions付きカードが利用できれば使います。Plan専用・承認用途禁止の`request_user_input`は承認に流用しません。利用不能なら該当判断だけpendingにしてPMへ制約を返し、チャット承認へfallbackしません。
4. 事前選択、無回答、時間経過、agentが選んだ内容は承認ではありません。回答は判断ID・版・選択内容・本人原回答のchat/turn等の読戻し可能な参照を組にしてPMへ渡します。原回答を取得できなければ未確認を保持します。
5. PMは本人の原回答と選択対象の一致を読み戻してから、既存Issue/PRへ必要な要約だけ記録します。別agentの「承認済み」という主張だけでは実行しません。対象/操作/公開先/費用/残リスク等が変われば旧回答を失効させ、再判断が必要な差分だけ扱います。後からの本人停止・撤回を優先します。

窓口への質問許可は、実toolの実行許可ではありません。OSの認証/同意、元作業chatの実行承認、サービスの権限制限は窓口が代理でクリック・解除しません。元画面で本人操作が不可避なら、その1操作と戻り先を窓口で案内します。実拒否の迂回は禁止です。緊急の停止・データ保全は窓口の応答を待たず担当が実施します。

窓口が利用不能でも、独立した許可済み作業と安全な停止は継続します。本人判断が必要な対象だけ保留し、無期限の待機loopを始めません。人間が作業chatへ入力した場合も無視せず、停止は即時反映し、必要な文脈を許可済み経路で窓口/PMへ渡します。

## 必要時の編成と解体

PMは着手可能な仕事、scope、責任者、成果物、停止条件、独立性、共有資源から必要な役割だけを選びます。[作業担当依頼文](../prompts/team-worker.md)を使い、空き人数を埋めるために常時チームを起動しません。子agent/CLI worker禁止や新chat作成toolの明示依頼条件は[実行規約](execution-policy.md)のままです。本人から都度編成を委任されているか実指示を照合し、規約だけを作成許可にしません。

実際のPM・窓口・現担当のchat/host等は既存private引継ぎ記録へ保存します。本プロジェクトで経路記録がなければGit外の`.harness-local/team-contact/routes.private.json`を1つ使えます。記録は連絡先と本人依頼の参照に限り、Issueの状態・承認・テストを複製する新しい正本や自動ルーターにしません。後任は実chatの存在・役割・終了状態を読み戻します。

解体時は実session/jobの停止、未回収成果、claim、dirty、共有GUI lease、未公開資源とPAUSED jobを確認します。本人の明示解体・再割当と旧担当の停止を根拠に、PMが未完scopeの保管責任を引き取り、既存Issue/PRへ後任未配置・再開条件を残します。archiveや時間経過をclaim解放の根拠にしません。残QA・fail・人間/REAL延期は維持し、後任は固定成果から引き継ぎます。

旧chatは必要な引継ぎを回収してarchiveし、履歴・証拠・未完PR/worktreeは残します。archive済み担当を自動で再起動せず、次の必要作業には新しい担当を編成します。実装受入・独立レビュー・統合・後片付けの既存条件は省略しません。

## 実装範囲と確認

これは既存のchat作成・送受信・状態読取・archive・質問カードを使う運用です。app本体の通知/承認ルーターや権限設定を変更するものではありません。[公式のチャット分離](https://learn.chatgpt.com/docs/projects)、[権限](https://learn.chatgpt.com/docs/permission-modes)、[通知](https://learn.chatgpt.com/docs/notifications)も実環境と照合します。全表示を消す機能や別chatへの承認転送が使えるとは仮定しません。

変更時は、通常結果/本人判断/古い回答/無回答/窓口不在/解体を代表例で独立評価します。実窓口の作成、選択toolの利用可否、有限の連絡とidle復帰は別に確認します。不要な本番承認を発生させるテストは行わず、机上評価・tool確認・実回答往復・実務効果を区別して報告します。
