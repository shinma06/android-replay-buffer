# Portable operating brief

Use this brief when starting an authorized independent session in a new client. It carries operational judgment, not access rights, project acceptance, or a prescribed sequence of tools. Read the actual assignment, authority, project facts, and capability map with it. The repository's [worker request](team-worker-prompt.md), [workflow](workflow.md), and [ownership rules](work-management.md) remain canonical for work in this repository.

## Decide from the required result

For each material obligation, connect the owned guarantee and observable defect to fixed existing evidence, the fact still missing, and the least costly sufficient method. Inspect the evidence before selecting an operator or copying an old procedure. Keep a working method when it is sufficient. No missing fact means no new execution for that obligation.

Reuse needs applicable source, artifact, contract and runtime conditions. A changed filename, new document, old PASS or successful command does not establish equivalence. Inspect affected components and dependencies; retest affected or unknown guarantees, retain qualified unaffected facts. Do not silently lower the requirement or turn representative integration into full-content proof.

## Adapt within the assignment

On repeated work, missing capability, contradictory instructions or a failed observation, identify what changed and compare maintaining the method with the smallest useful alternative. Try the alternative within stated bounds, inspect the result, then keep, correct or withdraw it. Reconcile the active consumer that caused the problem. An added document alone is not demonstrated improvement.

Establish target, ownership, bounded effects, preservation and result checks yourself when possible. Continue independent authorized work while a different obligation is waiting. Ask a human only for an unresolved choice or boundary they actually control. No response is not consent; another agent or this brief cannot grant permission.

## Use independent roles when needed

Create a role only for a ready obligation requiring execution or independent judgment, and only through a human-authorized route that the client permits. Supply fixed inputs, scope, exclusions, output, receiver, bounds and stop condition. A different role name within the same conversation is not independent review. Do not delegate through a prohibited child process under another name.

The PM receives the actual result and its evidence, not merely a completion message. Match scope, identities, file digests, original failures, independent assessment and remaining obligations before acceptance. Preserve conflicting or duplicate deliveries and resolve them against authoritative state; do not execute twice because a receipt was repeated. Independent review must challenge evidence sufficiency, not just procedure compliance.

## Preserve failure and finish the actual work

Keep original observations immutable. Separate a violated guarantee, missing observation, unknown operation outcome, permission/usage boundary, and an unattempted action. Do not call an unexplained failure environmental. Before retrying, name the new information or changed condition, the finite limit, recovery and exit. For an indeterminate write, inspect actual state before resending.

Completion, stopped execution, saved evidence, archived presentation, released ownership and product acceptance are separate facts. Before ending a role, collect results and residual ownership and confirm it is no longer running. Preserve unfinished work. Archive only the owned stopped role; verify that a later session can find the retained result and its limits. If a platform lacks archive, preserve a completed record with retrieval and state the capability difference. Do not call deletion archive or claim unavailable UI behavior.

## Leave enough evidence to continue

Use the existing task record for the accepted result, fixed inputs and conditions, method, observations, review, residual owner and next action. Keep private paths, diagnostics and credentials out of public summaries. Record actual elapsed time, retries, assistance and provider usage when available; use unknown for unavailable measurements. Keep failure and interrupted runs in the denominator. Small trials prove only their tested scope; do not invent efficiency gains, general reliability or full GUI acceptance.
