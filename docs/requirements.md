# 製品要件

この文書は、2026年10月3日の利用者との要件整理で合意した製品要件の正本です。目的と現行実装は[プロジェクト情報](project.md)、ビルド手順は[プラグイン開発手順](plugin-development.md)を参照してください。以下は要求する動作であり、実装・実機受入の完了記録ではありません。CLI原型の既存仕様・設定値は変更しません。

## 目的と開発順序

Android開発のIT（テスト）のエビデンス採取と、日常の動作確認で不意に発生した新規バグの調査を支援します。取得を有効にしておけば、事象の発生を予測して個別に録画を開始せず、必要な時に直前の画面操作とログを1ボタンで保存できることを目指します。

1. **Android Studio内で初期版を完成させる。** macOSを最優先に実装・検証する。
2. **初期版完成直後、最初にmacOSメニューバー連携へ着手する。** IDEを前面にしなくても主要な操作を行えるようにする。
3. **Windows、Linuxの順で対応を広げる。** プラグイン化の目的には複数OSでの使いやすさが含まれるため、最初から他OSへの展開を考慮する。初期版をmacOS専用構造へ固定しない。

後続TODO同士の細かい着手順は未定です。メニューバー連携の「初期版直後に最初」という順序と、OSの優先順は維持します。対応OS・端末・IDE版の保証範囲は各環境の実受入後に公表します。

## 初期版の確定要件

### 対象と導入

| ID | 要件 |
| --- | --- |
| ENV-01 | 1プロジェクト・1台での利用を前提にする。複数プロジェクトでの同時利用や設定・取得の共有方式は初期版では検討対象外。 |
| ENV-02 | Android実機とAndroid Emulatorの両方を対象にする。初期版は合わせて1台。 |
| ENV-03 | Android StudioでAndroid開発ができる環境を前提に、録画・ログ取得のための追加ツールの個別インストールやPATH設定を利用者に求めない。必要な準備はプラグイン側で行う。同梱・取得方法や録画エンジンは未選定。 |

### 有効化・設定

ここでの「無効」はプラグイン内の機能トグルを指し、IDEのプラグイン無効化・アンインストールとは区別します。

| ID | 要件 |
| --- | --- |
| CTL-01 | 機能の有効・無効トグルを用意する。有効時は端末接続を契機に自動取得し、有効に切り替えた時点で接続済みなら即座に取得を開始する。未接続なら接続待ちにする。 |
| CTL-02 | 初回は無効。有効・無効の状態を保持し、Android Studioの次回起動でも復元する。有効なら端末接続に応じて自動取得する。 |
| CTL-03 | 無効化すると録画・ログ取得などの取得機能のバックグラウンド処理を停止し、未保存バッファを破棄する。保存済みエビデンスは残す。 |
| CTL-04 | 有効・無効にかかわらず設定画面を表示し、設定を編集できる。無効時に設定メニューを隠したり、設定項目を操作不能にしたりしない。 |
| CTL-05 | 取得中に設定を編集しても、その時点では取得条件を変えない。利用者の明示的な「適用」操作で反映し、必要なら取得処理を再起動する。機能全体の有効・無効トグルはCTL-01/03どおり即時に動作する。 |

### バッファと継続取得

| ID | 要件 |
| --- | --- |
| BUF-01 | 保持時間の初期値は**180秒**。設定画面で変更できる。画面録画とログを継続取得し、直近の設定時間分を更新しながら保持する。 |
| BUF-02 | 保存時は、設定時間の範囲内で取得できた時間分を最大限保存する。取得開始から20秒しか経っていなければ20秒分を保存し、設定時間が満ちるまで保存を待たせない。 |
| BUF-03 | 保持時間は中断・空白を含む**実時間**で数える。直近60秒のうち20秒が欠落した場合、対象は直近60秒で取得できた40秒分。取得できた60秒を集めるために対象時間を過去へ広げない。 |
| BUF-04 | 保存処理中も取得を継続し、保存後もバッファを消さない。続けて保存した結果の区間重複を許容する。試験手順を間違えても取得を止めずにやり直せる。 |
| BUF-05 | 端末切断時は取得を停止し、切断直前のバッファを保存可能な状態で保持する。再接続時は自動取得を再開する。機能を明示的に無効化した場合はCTL-03を優先する。 |
| BUF-06 | 録画・ログ取得が途切れたら直ちに自動復旧を試み、取得可能になり次第再開する。中断・再開で記録シーケンスを分断したりバッファ全体をリセットしたりせず、同じシーケンスを維持する。保存済み成果物は上書きしない。 |
| BUF-07 | 動画・ログの一方に障害が起きても、取得できる側は継続する。保存も取得できたデータで行い、不足している種類を画面上で明示する。空白期間を取得成功と扱わない。 |

「同じシーケンス」は中断前後の経緯・時刻関係を維持するという製品要件です。動画内部の分割単位やファイル結合方式までは指定しません。取得可能量が0の場合、長い切断中の保存基準時刻・保持期限、再接続後の古い区間の更新規則は、BUF-03/05と矛盾しないよう同期・障害時UXの検討で具体化します。無制限の一時データ蓄積を決めたものではありません。

### ログと動画・ログの対応

| ID | 要件 |
| --- | --- |
| LOG-01 | **端末全体のlogcatと対象アプリのlogcatを、別データ・別ファイルで保存**する。取得内部を別プロセスにするか、同一取得から抽出するかは未定。 |
| LOG-02 | 対象アプリはAndroid Studioの実行対象からの自動選択を基本とし、プラグイン内でpackage名を手動指定して変更できる。自動選択と手動指定の両方を備える。 |
| SYNC-01 | **動画の場面と、その時点のログを対応づけられることは必須。** 端末全体・対象アプリの両ログを対象にし、中断・再開・空白期間・保存区間の切り出し後も時間的な対応と欠落を確認できるようにする。同期方式・精度基準・保存形式・表示方法は検討タスクで決める。 |

自動選択できない場合の案内、実行対象の切り替えやアプリ再起動時の追従、手動指定の優先・解除規則は、実装前に定義します。未決のケースを理由に、決定済みの全体ログ取得や手動指定を省略しません。

### 保存と表示

| ID | 要件 |
| --- | --- |
| SAVE-01 | 初期版は**設定した保持時間分を1ボタンで保存**する。保存時の長さ選択は後続TODO。BUF-02/03に従い、実際に取得できたデータを対象にする。 |
| SAVE-02 | 設定画面で保存先フォルダを指定し、保存ごとに日時付きフォルダへ動画と2種類のログをまとめる。毎回の保存先選択・名前入力は求めない。同じ日時の保存でも既存成果物を上書きしない。具体的な命名規則・拡張子は未定。 |
| SAVE-03 | 保存完了を通知し、通知から保存先フォルダを開けるようにする。 |
| SAVE-04 | 保存済みエビデンスはプラグインが自動削除せず、利用者が手動管理する。保持時間の制限は保存前の一時バッファにのみ適用する。 |
| SAVE-05 | **保存失敗時のUXは未決。** 再試行・失敗対象の一時保持・破棄・保存先変更・ディスク不足時の取得継続などを検討する。会話中に提示した「保持して再試行する案」は採用決定ではない。 |
| UI-01 | 対象端末・対象アプリと、無効／接続待ち／取得中／復旧中／一部取得失敗が分かる表示を備える。動画とログのどちらが取得できていないかを区別できるようにする。 |
| UI-02 | 保存ボタンなどを置く入口は、Logcat内か独立したツールウィンドウかを検討する。現時点でどちらも採用決定ではない。 |

## 実装時に具体化する受入例

以下は将来のCase作成の入口であり、試験実施済み・passではありません。実装Issueで対象build・実機/Emulator・手順・期待値・同期精度を固定し、[受入手順](verification/README.md)のCaseへ接続します。

| 場面 | 確認したい結果 |
| --- | --- |
| 初回起動、接続済み端末で有効化 | 初回は無効、設定は編集可能。有効化で即取得開始し対象と状態が分かる。 |
| 有効のままIDEを終了・再起動 | 有効状態が復元され、端末接続に応じて取得する。 |
| 180秒設定、開始20秒後に保存 | 取得済み20秒分の動画と各ログを同じ保存単位で残す。 |
| 60秒設定、10秒間隔で2回保存 | それぞれの直前区間を保存し、重複を許容。保存で取得やバッファが途切れない。 |
| 60秒内に20秒の中断 | 実時間60秒の中で取得済み40秒を対象とし、中断前後を同じシーケンスとして識別できる。空白を詰めて時刻対応を誤らせない。 |
| 端末切断・再接続 | 切断前データは保存可能で、接続可能になれば自動再開。長い切断の保存境界は検討結果に従って確認する。 |
| 動画だけ／ログだけの障害 | 残る取得は継続し、不足を表示。復旧後も同じシーケンス。 |
| 取得中に設定編集・適用 | 編集だけでは取得条件不変。適用で変更し、必要な取得処理の再起動を行う。 |
| 無効化 | 取得処理停止・未保存バッファ破棄。保存済みデータと設定画面は残る。 |
| 保存結果の確認 | 日時フォルダ内の動画・2種類のログ・同期情報を照合し、通知からフォルダを開ける。保存済み成果物は時間経過で自動削除されない。 |
| 録画中に回転 | 初期版でも致命的な障害や保存済みデータ破損を起こさず、取得中断時には復旧する。完全な回転追従の合格とは区別する。 |
| 新しい利用環境 | macOSを先に、実機とEmulatorで、利用者の追加ツール手動導入・PATH設定なしに取得・保存できる。Windows/Linuxはそれぞれの検証後に対応済みとする。 |

### タイムライン同期の参考案

利用者から提示された[参考会話](https://chatgpt.com/s/t_6ac0fb3a3d7081918ed29419471de79f)と、その転載内容を調査の入口とします。リンクの取得はできなかったため転載内容を基に整理しています。技術的成立や仕様の正しさは、調査Issueで一次情報と試作を用いて確認します。

- 動画とログで対応可能な時間基準を持つ。相対時刻、単調増加時計、動画PTSとの対応、複数時計間の変換は調査候補。
- MP4＋JSONL＋セッション情報などの別ファイル方式、WebVTT metadata、Perfetto、MKV metadata trackは比較候補であり、いずれも採用必須ではない。
- 選定では同期精度・データ量・欠落表現・可搬性・保存後の確認のしやすさを比較する。
- 専用ビューア、単一ファイル化、AI解析、HTTP/DOM/クリック等の新規イベント取得は、この参考案だけを理由に必須機能へ追加しない。現時点の取得対象は画面映像とlogcat。

## 未決事項の扱い

未決事項を実装担当が暗黙の製品仕様へ変えないよう、実際の設計で候補・影響・採用理由を記録します。保持時間の許容範囲、固定画質の数値、復旧の再試行間隔、設定反映に伴う再起動時の未保存データ、対象アプリの切替規則、保存失敗時の一時データ、長い切断時のバッファ境界、OS/IDE/端末の対応範囲、依存ツールの提供方法、同期精度・保存形式はまだ確定していません。

これらの技術設計は[共通IDE知見](android-studio.md)の該当範囲を固定SHAで確認して進め、実際の設計を `docs/plugin-design.md` に記述します。現行CLIの構造や参考案を、そのまま将来プラグインの方式と決めたものではありません。
