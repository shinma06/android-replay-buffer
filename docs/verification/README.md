# 検証方針

## developへの統合

CIの `test` と `os-parity`（macOS・Windows）が通れば、`develop` へ統合できます。レビュー・統合の手順は [AGENTS.md](../../AGENTS.md) に従います。製品仕様は [要件](../requirements.md) と各設計文書が正本です。

変更に関係する自動テストを追加・更新し、保存内容・時刻対応・互換性・失敗時のデータ保全を確認します。実際に見つかった不具合は修正します。自動テストの合格と、IDE・端末での動作確認は区別します。

VMや実機で観察できない項目は **「未検証（理由）」** と記録するだけで、`develop` への統合を止めません。PNG保存後のOS通知など、外部環境で観察できない項目も同じ扱いです。旧運用の台帳・承認・追加Issueの作成を統合条件にしません。

## mainへのリリース

`main` 昇格時のみ、`develop` 先頭のCI ZIPを使って [VMでのIDE・エミュレータ受入](vm-acceptance.md) を実施します。版番号・公開の手順は [リリース規則](../release.md) に従います。通常の `develop` 統合や `early` の更新には、この受入を要求しません。

## 記録

証拠はPR本文に要点だけを残します。

- 対象commit、実行したテストと結果。
- IDE・端末で確認した場合は対象の版と結果。
- 確認できなかった項目と「未検証（理由）」。

検証用のJSON台帳は作りません。録画・logcat・生の診断情報・認証情報は公開しません。製品が生成する `replay.json` やJSONL、テスト用fixtureは検証台帳とは別で、引き続き維持します。

旧規約・検証記録の復元先は [旧運用の保管先](../legacy-ops/README.md) を参照してください。これらは履歴であり、現行の作業規約ではありません。
