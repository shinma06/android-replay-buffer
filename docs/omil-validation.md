# 新しい環境で運用を確認する

この入口は、既存の[割当と受領](team-worker-prompt.md)を別セッション・別clientへ渡すときに使います。一般原則は[portable brief](omil-portable.md)、ARBの実作業は[プロジェクト情報](project.md)、[実行規約](execution-policy.md)、[正式受入](verification/README.md)へ接続します。新たなcoordinator、常駐監視、権限付与の仕組みは追加しません。

## 実証用の入力

```bash
python3 scripts/workflow/omil_fixture.py /tmp/omil-trial-a --variant a
```

出力は人工ログと架空の受領履歴だけです。既存directoryを上書きせず、入力一式の実SHA-256をmanifestへ記録します。別providerへ渡す前に、生成されたpackと利用するprovider・実行権限・費用範囲を確認します。privateな元観察、会話、認証情報、実device情報は生成しません。

同じ条件の比較では、旧規約を渡すREFとportable briefを渡すNEWを分離し、同じ資料や正解を混ぜません。非GPT/非CodexのALTではPMの判断・役割制御・実行・評価も別基盤で行います。Codexが各判断を代行して出力だけ別モデルへ書かせる方法では成立しません。別OSは必要な能力差がある場合に選び、clientの変更とOSの変更を混同しません。

各試行は新PMと必要な独立役から開始し、通常、根拠付きの再利用、変更された成果、不足観察からの有限回復、権限境界、受領不整合を扱います。陽性/陰性の両方を含む入力を使い、常に空出力にする検査を合格させません。原資料と評価者の期待値を渡さず、実セッションの操作履歴で参照範囲を確認します。同じOSユーザーのdirectory分離はセキュリティ隔離ではなく、期待値へのアクセスを構造的に禁止する仕組みとは呼びません。

配布するcase名と配送名は判定結果を含めません。variant bではID/時刻だけでなく受領の正誤を入れ替え、同じ名前から答えを選べないようにします。実際の契約・許可状態・模擬応答は判断の根拠なので隠しません。生成された後続観察を読むことは新しい実機採取ではなく、重複レコードの判定は実配送サービスの耐障害性試験ではありません。

## 何を確認するか

ファイルの存在や自己申告だけでなく、独立役の実生成、固定入力からの出力、独立した根拠評価、PMの受領、停止と保存、後の再参照を確認します。能力がなければその部分を未実施として残します。人工fixtureの拒否や故障は模擬であり、実サービスの拒否・製品の不具合へ読み替えません。

生成packは手段を決める練習と欠陥検出に使います。実案件への適用は、対象source/契約/artifact/条件の代表scopeについて別途証拠を読み、必要な実検査を行います。人工試験だけでARBの全運用移行や製品のGUI受入を主張しません。既存の初期版証拠・FAIL・REAL/人間延期は保持します。

試行数、時間・容量・費用の上限、期待する品質、測定開始/終了、支援の記録は開始前に当該Issue/実行packetへ固定します。数値を恒久規約にしません。必須品質を満たすかと効率が改善するかは別に判定し、比較できる実測がなければ改善率を示しません。通常の可逆的な方法選択まで新しい本人承認gateへ戻さず、実際の権限・支出・共有先・価値判断の未解決差分だけを扱います。

採用時は、割当を生成する実consumerと受領時の判断がbriefの根拠へ対応することを確認します。結果、是正、維持/採用/撤回と残ownerは既存Issue/PRへ残し、別台帳を増やしません。実施結果の正本は[#266](https://github.com/shinma06/android-replay-buffer/issues/266)です。本書やfixture生成成功自体は運用実証の合格記録ではありません。
