# 運用の移植性と目的への進み方を確認する

この入口は、既存の[割当と受領](team-worker-prompt.md)を別セッション・別clientへ渡すときに使います。一般原則は[portable brief](omil-portable.md)、ARBの実作業は[プロジェクト情報](project.md)、[実行規約](execution-policy.md)、[正式受入](verification/README.md)へ接続します。新たなcoordinator、常駐監視、権限付与の仕組みは追加しません。

## 移植性の受入

目的・役割・入力/出力・品質・証拠を、GPT/Codex固有の環境、API、session形式が必須でない共通契約として読めることと、実consumerがその契約を利用することを確認します。別エージェントや別OSでの実行実証を、この確認の必須条件にはしません。効率よく使えているCodexの機能は実装手段として残し、全clientを同じ最小機能へ揃えません。

割当では必要な能力と実際の利用手段を対応させます。例えば独立役の実在と受領は必要な事実ですが、特定のchat作成tool、UUID形式、archive UIは共通の成果条件ではありません。原本の同一性、権限、独立性、停止・再参照の証拠を保ち、名前の置換や自己申告だけで同等としません。既存のIssue/PRと共有成果を使い、本人による成果転送を通常工程へ戻しません。

ARBのCodex CLI worker、Codex origin adapter、設定済みのremote Code Reviewは現在の環境に対応した実装です。移植先の汎用taskへ、その環境変数や完了形式を必須条件としてコピーしません。[対応する選択入口](setup/automation.md#レビュー元と実行元の選択)から、完了元と信頼された実行元を接続します。旧receipt・独立性・全binding・未完了依頼の保証は保持します。host embedding APIの対応と別providerでの実接続/実行実証は区別し、未対応の接続を対応済みとは呼びません。

## 実証用の入力

```bash
python3 scripts/workflow/omil_fixture.py /tmp/omil-trial-a --variant a
```

この人工fixtureは、判断方法に具体的な不足があり試行が必要な場合に使います。移植性の確認だけを理由に新しいmodel、参加者、同一試行を追加しません。出力は人工ログと架空の受領履歴だけです。既存directoryを上書きせず、入力一式の実SHA-256をmanifestへ記録します。外部へ渡す場合は実際の共有先・権限・費用条件を確認します。privateな元観察、会話、認証情報、実device情報は生成しません。

方法を比較する必要がある場合は、同じmodel、同じ目的・品質と比較可能な作業時間/資源で、旧方法と変更後の方法を分けます。先行結果や正解を混ぜず、条件差と支援を残します。異なるmodelの出力、費用上限の縮小、早い打切りを運用効率の改善へ換算しません。既存の固定結果で足りる義務は再実行しません。

新規sessionの再現を試す場合は新PMと必要な独立役から開始し、通常、根拠付きの再利用、変更された成果、不足観察からの有限回復、権限境界、受領不整合を扱います。陽性/陰性の両方を含む入力を使い、常に空出力にする検査を合格させません。原資料と評価者の期待値を渡さず、実セッションの操作履歴で参照範囲を確認します。同じOSユーザーのdirectory分離はセキュリティ隔離ではなく、期待値へのアクセスを構造的に禁止する仕組みとは呼びません。

配布するcase名と配送名は判定結果を含めません。variant bではID/時刻だけでなく受領の正誤を入れ替え、同じ名前から答えを選べないようにします。実際の契約・許可状態・模擬応答は判断の根拠なので隠しません。生成された後続観察を読むことは新しい実機採取ではなく、重複レコードの判定は実配送サービスの耐障害性試験ではありません。

clientが注入する指示と必須Skillも実行条件です。開始前に許可する一般Skillの参照元・hash・用途を明示し、実際の追加読取を残します。配布packだけの指示で上位の実行規約を無効化せず、未記録の追加contextがあれば、その影響と証明範囲を評価します。

## 品質と実行範囲

実行した試行では、ファイルの存在や自己申告だけでなく、独立役の実生成、固定入力からの出力、独立した根拠評価、PMの受領、停止と保存、後の再参照を確認します。能力がなければその部分を未実施として残します。人工fixtureの拒否や故障は模擬であり、実サービスの拒否・製品の不具合へ読み替えません。後から不要になった試行は未実施の履歴を保って対象外へ変更し、成功や許可取得へ読み替えません。

生成packは手段を決める練習と欠陥検出に使います。実案件への適用は、対象source/契約/artifact/条件の代表scopeについて別途証拠を読み、必要な実検査を行います。人工試験だけでARBの全運用移行や製品のGUI受入を主張しません。既存の初期版証拠・FAIL・REAL/人間延期は保持します。

## 運用効率の判断

まず目的を満たす成果と必須品質を決め、その成果へ同じmodel・比較可能な作業時間/資源でどれだけ進めたかを見ます。十分な根拠の再利用、影響に比例した検査、重要な曖昧さの早期解消、feedbackによる手段の修正を評価し、待ち・手戻り・重複検査・管理作業が減ったかを実記録と結びます。変更前から十分だった方法を不要に置き換えません。

停止や本人介入を分析するときは、同じ停止の再報告を重複加算せず、原返却・対象の実状態・止まった最小scope・本人による転機・実際の解消と回避を分けます。確認できる期間・母集団・時刻対応だけを使い、質問から回答までの時間を全体の停止時間とみなしません。少数の成功例だけでなく、実欠陥、必要な独立評価、本人だけが知る事実、明示pauseも対照に含めます。

割当と受領では、止まった同じ目的を満たす別手段と、別のREADYな目的関連作業の両方を検討します。原因・不足事実・解消見込み・限定コストから選び、作業切替えだけで元の停止を解消済みにしません。旧指示が原因なら実consumerを修正し、必要な小試行とfeedbackを根拠に維持/採用/修正/撤回します。

比較する場合は、完了した保証と残件に加え、実作業/待ち時間、再試行、人の支援を取得できる範囲で残します。記録を取る負担自体も考慮し、常時監視や新しい計測基盤は追加しません。必須品質の達成と効率改善は別に判定し、比較条件や実測が不足すれば改善率は未証明とします。支出削減や任意の停止上限を主要な成功指標にしません。

必要な試行の品質、開始/終了、支援、回数・時間・容量・実費用の制約は当該Issue/実行packetへ記録し、数値を恒久規約にしません。本人・toolの実制限は保持します。通常の可逆的な方法選択まで新しい本人承認gateへ戻さず、権限・支出・共有先・価値判断の未解決差分だけを扱います。

採用時は、割当を生成する実consumerと受領時の判断がbriefの根拠へ対応することを確認します。結果、是正、維持/採用/撤回と残ownerは既存Issue/PRへ残し、別台帳を増やしません。初期実施結果は[#266](https://github.com/shinma06/android-replay-buffer/issues/266)、後続A/B/Cの限定結果・採用条件と旧判断の対応は[現行判断](omil-current.md)から参照します。本書やfixture生成成功自体は運用実証の合格記録ではありません。
